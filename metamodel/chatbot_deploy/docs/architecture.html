Key Design Constraints

Stateless Backend

The API holds zero session state. Every request carries the full conversation history. Session is maintained entirely in the browser (state.messages[]).

No Streaming

The /api/chat endpoint is synchronous. The full Claude + tool loop completes before any bytes are sent. Loading phrases on the frontend are purely cosmetic timers.

Surrogate ≠ SISEPUEDE

The XGBoost model is a statistical approximation trained on ~99,000 SISEPUEDE scenarios. It predicts per-sector emissions and cost/benefit at five reporting years (2025/2035/2040/2050/2070), not full year-by-year trajectories.

Assistant-Controlled Charts

Charts are not auto-rendered. The assistant decides which (if any) help and places each one inline by writing a ```chart``` block. Three templates exist: stacked emissions by sector, total-emissions timeseries, and a cost/benefit diverging bar chart.

Frontend Layer

A single-page HTML/CSS/JS app served as static files by FastAPI. No build step, no framework.

Agent Tool Loop

def run(messages, locked_overrides):
    tool_calls_log = []
    client = Anthropic(api_key=...)
    system_prompt = _build_system_prompt()     # Loads feature_registry.json each call

    for iteration in range(5):                 # Max 5 tool iterations
        response = client.messages.create(
            model=settings.claude_model,       # claude-sonnet-4-6
            system=system_prompt,
            tools=TOOLS,
            messages=anthropic_messages,
        )

        if response.stop_reason == "end_turn":
            return {reply, simulation, scenario_interpretation, tool_calls_log}

        if response.stop_reason == "tool_use":
            for tool_block in response.content:
                result, sim_data, interp = _execute_tool_call(tool_block, ...)
                tool_calls_log.append({tool, inputs})
                # append tool result to history and loop
Concrete example — "What if Uganda aggressively protects its forests?"

1. anthropic_messages = [{"role": "user", "content": "What if Uganda aggressively protects its forests?"}]
2. Claude API call (iteration 0) → stop_reason = "tool_use". Claude calls run_simulation(scenario_name="Forest Protection", lever_overrides={"15": 0.9, "9": 0.9}) — group 15 (reduce deforestation) + group 9 (increase forest sequestration).
3. Backend executes _run_simulation_tool: builds the 67-feature vector, runs XGBoost for scenario + BAU baseline. Tool result (JSON summary incl. sector_breakdown + cost_benefit_by_year) appended to anthropic_messages as a tool_result message.
4. Claude API call (iteration 1) → stop_reason = "end_turn". Claude reads the numeric results and writes the markdown narrative response.
5. Loop exits. Returns {reply, simulation, scenario_interpretation, tool_calls_log} to FastAPI.

In this example the loop runs 2 iterations. If the user had also asked "and what does current deforestation look like?", Claude would insert a second get_country_context(topic="agriculture") call at step 2, making it 3 iterations total.

LHS → S3 Lookup Chain (get_scenario_variables)

When Claude calls get_scenario_variables, s3_lookup.py resolves the user's L values to a pre-computed SISEPUEDE experiment in four steps:

L values  {group_id: float in [0,1]}   ← raw policy values, NOT T-transformed
  │
  │  1-NN Euclidean search against all rows in ATTRIBUTE_LHC_SAMPLES_LEVER_EFFECTS
  │     where design_id = 4 (the ~100k LHS scenarios — L and X vary together; this run
  │     has NO L-only design). Joint L distance: dist = sqrt( Σᵢ (trial_i − query_i)² )
  ↓
nearest future_id                       ← intermediate identifier, never leaves s3_lookup.py
  │
  │  Join ATTRIBUTE_PRIMARY on (design_id=4, future_id)
  ↓
primary_id  (int)                       ← stable experiment identifier used for all S3 reads
  │
  │  Look up directory_n in s3_model_input_index.json
  │  (pre-built Athena index: primary_id → batch file number)
  ↓
s3://sisepuede-data/run_database/{run_id}/model_output/region=uganda/model_output_{n}/data.csv
  │
  │  Filter CSV rows to primary_id, extract emission_co2e_subsector_total_{sector}
  ↓
sector emission trajectories  [Mt CO₂e × 56 time periods]   ← returned to Claude
Note: The L→T formula (T = 0.9×x + 0.1) is not applied in the lookup. The LHS CSV stores raw L values in [0,1], so the search compares like-with-like. T is only computed by predictor.py when building the XGBoost input vector. Because design_id=4 perturbs X alongside L, the matched trial is the closest by L but its X is also varied — so get_scenario_variables returns an approximate nearest experiment, not an exact L-only match.

L Transform Formula

T = 0.9 × x + 0.1   (the standard policy design)

x = L feature value ∈ [0, 1]
T = transformation magnitude ∈ [0.1, 1.0]
Physical effect = transformer_default_magnitude × T

Reverse:  x = (T − 0.1) / 0.9
Example:  x = 0.9  →  T = 0.91  →  91% of maximum ambition

Ramp: SISEPUEDE applies T progressively over ~20–30 years via vec_implementation_ramp.
T is the TARGET at 2070, not an immediate jump.
L vs T — what goes into XGBoost: The formula T = 0.9 × L + 0.1 explains what an L value means physically in SISEPUEDE (used by get_scenario_variables → S3 lookup). XGBoost itself takes raw L values directly — it was trained on LHS samples where inputs are L ∈ [0, 1]. The T transform never touches the model.

To convert a physical target to an L value: L = (T − 0.1) / 0.9, where T = physical_target / transformer_default_magnitude.
Example: "achieve 70% of max renewable capacity" → T = 0.70 → L = (0.70 − 0.1) / 0.9 = 0.667

XGBoost Model Variants — Comparison

Historical comparison. The R² tables in this section come from an earlier architecture-selection run: two variants of the sector model trained on the then-1,840-scenario dataset and evaluated on a held-out test set (N = 368), against 59 targets. They were used to pick the architecture (MultiOutputRegressor, Variant A) — they are NOT the current model's metrics. The deployed model was since retrained on the current ~99,000-scenario run and expanded to 175 targets (5 reporting years, 15 sectors, disaggregated cost/benefit + per-year GDP). Per-target R² for the current model is printed by retrain_sector.py.

Variant A — Selected (deployed)

MultiOutputRegressor(XGBRegressor)
One independent gradient-boosted tree per target.
File: xgb_pipeline_sector_independent_*.pkl
Mean R² across all 59 targets: 0.951

Variant B — Not selected

XGBRegressor(multi_strategy='multi_output_tree')
Single shared tree structure across all targets (XGBoost 2.0+ native).
Mean R² across all 59 targets: 0.704

Why Variant A was selected: It dominates on every sector×year target by R² gaps of 0.2–0.6. Variant B has a slight edge on 3 aggregate emission totals (emission_total_sum, 2066_2070_mean_emission) but performs catastrophically on cost, co-benefit, and sector breakdown outputs — making it unsuitable for a policy tool where financial metrics and sector attribution matter.

LHS Trial Lookup Flow

# When get_scenario_variables is called:

1. load ATTRIBUTE_LHC_SAMPLES_LEVER_EFFECTS.csv  (local)
2. Filter to design_id=4 rows
3. Compute Euclidean distance from requested L values to each trial row
4. Select the nearest trial → future_id

5. Lookup future_id in ATTRIBUTE_PRIMARY.csv → primary_id
6. Look up primary_id in s3_model_input_index.json → directory_N

7. Fetch s3://sisepuede-data/run_database/{run_id}/model_input/region=uganda/
        model_input_{directory_N}/data.csv   (S3, cached LRU 50 entries)

8. Filter CSV to primary_id row → return variable values for requested groups
